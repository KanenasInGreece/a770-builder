# Changelog

This file records security changes that are not yet a release. The published cut stays v0.5.8. The version number does not move in this change.

## Unreleased

### Compromised emSign root in TLS trust bundles

In October 2026, eMudhra intermediate keys that chain to the root named `emSign ECC Root CA - G3` were compromised. A client that still has that root in its own bundle will accept a certificate an attacker signs with those keys. Three roots with similar names, `emSign Root CA - G1`, `emSign Root CA - C1`, and `emSign ECC Root CA - C3`, were not part of that incident and are not what this change removes.

The packages that still trusted the compromised root, and the versions that stop trusting it:

- certifi below 2026.10.19 (GHSA-6q48-6c7w-9gw2). This tree uses certifi 2026.10.23. The 2026.10.18 upload was the first removal; 2026.10.19 put back the unaffected emSign roots and is the floor.
- uv below 0.13.4 (GHSA-hq85-5cpj-mr62). uv carries its own copy of the bundle, so an updated operating-system store does not fix an old uv. This tree uses the uv 0.13.5 static binary.
- pip below 26.2.2. Older pip vendors its own certifi and keeps trusting the root after the operating system has dropped it. A distribution pip that reads only the system trust store follows that store.

What the review found on the host, and what was not bumped:

- The `uv` on `PATH` was already 0.13.5, and its binary does not contain the root.
- The tool set this project installs with `uv run --with` and `uvx --from` resolves to pytest 9.1.1, pytest-asyncio 1.4.0, tokenizers 0.23.3, huggingface-hub 2.3.0, certifi 2026.10.23, and shellcheck-py 0.11.0.1. An OSV query of that set reported no known vulnerabilities. There is no project lockfile to retarget.
- No `cacert.pem` under the seat cache or the uv cache still named the root.

What was still exposed, and what changed:

- `harness/env.sh` now refuses to load when `uv` is missing or older than 0.13.4. The sandbox bind-mounts whichever `uv` is on `PATH`. An older binary would make package fetches from the host trust the compromised root. The check runs before any path or knob is read.
- Vulkan llama.cpp. The previous pin was build 10902 (`sha256:33ed2a8936e94ac893a50eed3d2958141d352198233d107e58c1c7ee3b96a9b4`). That image had certifi 2026.07.22 and uv 0.12.13, and the root was present. It is also inside the window for CVE-2026-107183, a use-after-free in llama.cpp's chat-template mapper, fixed before build 11393 and reachable through `POST /completion` when a chat parser is in use. The tracked example and this host's `compose/a770-vulkan.env` now pin `ghcr.io/ggml-org/llama.cpp@sha256:f0be303ba81eafe6abd5d4a7aef4eaa64a6b394b5c5878280598b3fbcb790ba6` (build 11870). Inside that image: Python 3.13.17, certifi 2026.10.23, uv 0.13.5, and the root is absent from the bundles and from the uv binary. No local rebuild was required.
- Intel SYCL llama.cpp. The previous local pin was `sha256:7b4905e41d2720bfccf390e78e938e8148329b3da9467d3f1b008f0efc44cd97`. The current upstream full image is build 11870, `sha256:b763b3587a8fd40f7575d8a12b38071cc2ed8a88086925e6936da7727723412f`. Its virtualenv already had pip 26.2.2 and certifi 2026.10.23. Ubuntu's pip under `/usr/lib/python3/dist-packages` still had the root, and that pip cannot be uninstalled (Debian shipped it without a RECORD file). `compose/refresh-ca.Dockerfile` keeps the server binary, copies the virtualenv's clean bundle over every `cacert.pem` that still contains the root, and refuses to finish if the root remains. This host's built image is `a770-builder/llama-intel-ca@sha256:03f25fa595d0cf34eb054516c6beaf96d52d5bf90476916aa6cc804f60ae30e9`. The named system certificate is gone, the conf line is gone, OpenSSL does not read that subject from the system bundle, and a text scan of the other bundles found zero copies of the root. The unaffected emSign roots C3, C1, and G1 remain. The entrypoint is still `/app/tools.sh`.
- vLLM. `intel/llm-scaler-vllm:0.26.0-b2` and the tag `1.5` are the same image, `sha256:52218ad85513ab6686d4c090c83c2bd8c5b02423c63aa4dabd41837fe641fe3b`, published before the incident, with certifi 2026.07.22. No newer published tag of that engine is past the incident. The experimental `0.31.0-b1` tag is also older than the incident and was not used. The same Dockerfile upgraded the virtualenv to pip 26.2.2 and certifi 2026.10.23 and replaced the Ubuntu pip bundle. This image has no uv binary. This host's built image is `a770-builder/llm-scaler-vllm-ca@sha256:0d838dca8939e1600dfc231163c7fb47bd454ba94155a9590e08a755315d4712`. The named system certificate is gone, the conf line is gone, OpenSSL does not read that subject from the system bundle, and a text scan of the other bundles found zero copies of the root. The entrypoint is still the oneAPI `setvars` line followed by `vllm serve`.
- Flash-Next SGLang. The trial image `sha256:24c872759256d4b0d3b9d0419ebdf6f3547e0fdbd3891fbb9f90e32ad255c94f` vendors certifi 2026.07.22 and uv 0.12.16. The registry listing for a newer tag was refused, so there was no newer image to retarget. The Dockerfile upgraded pip and certifi, replaced uv with 0.13.5, deleted the uv and pip wheel caches (a cached wheel still held the old bundle after the first attempt), and replaced the remaining bad bundles. This host's built image is `a770-builder/sglang-flashnext-ca@sha256:9c1cb2a18afd68696500ad1ba02ab65def837e54068d4a0164bcf1f162762215`. `uv` and `uvx` both report 0.13.5 and do not contain the root. The three local image ids exist only on the machine that built them. Another host builds `compose/refresh-ca.Dockerfile` from the base digest named in the matching `compose/*.env.example` and pins the id that build prints. The tracked default is the local tag, not the vulnerable upstream digest, so a checkout that has not built the refresh does not start the old image. `local-build.sh doctor` still warns while an env line is a tag rather than an id.

Compose sets the container user from `A770B_CONTAINER_UID`. The Dockerfile's `USER root` applies to the build. The server process user is unchanged.

### Review of that change

A read of the first commit found holes in the rebuild and in what a host can still start. The fixes:

- The uv binary is copied from `ghcr.io/astral-sh/uv` digest `sha256:32a7bb39b496babbd997b0a39a4d66c126bdaf5661b302bf6f06abda8deca6ff`, not from a floating tag. Every file named `uv` or `uvx` under the image is replaced, and each of them is scanned.
- pip 26.2.2 and certifi 2026.10.23 are installed with `--require-hashes`. A download that travels through the old trust store cannot substitute a different wheel. The hashes are the PyPI wheels `fd7f4dfa8190e014013b9f08f3e973f4e4c26ffd179a204895533a7254813a70` and `e9b54de76e530bb6cf0ccd036787103acb58fd42ba930ea8bf948ddbaa2f61d1`.
- The build fails if the root remains in any `cacert.pem` or in `ca-certificates.crt`. The system store is not replaced with the certifi bundle. A text scan of that store missed the certificate: its name is inside the certificate, not written out as text. The earlier check could treat a mixed `find` result as clean. The result is now the list of files that still contain the root.
- The Intel, vLLM, and SGLang compose files set `pull_policy: never`. The default name is a local build. Without that, compose would pull `a770-builder/...` from Docker Hub, a name this project does not publish.
- Serve refuses four published digests that still contain the root: Vulkan `33ed2a8936e9`, the older Intel pin `7b4905e41d27`, vLLM `52218ad85513`, and SGLang `24c872759256`. Doctor warns on those names and still passes. A digest that is not one of those four stays silent.
- The measured vLLM row names the local image `exl3xpu:b70-15ded2f`. That name stays in the registry. On this machine the image's virtualenv certifi was 2026.07.22, so it was rebuilt with the same Dockerfile and tagged with the same name. Its local id is now `sha256:b9d83f2e4db86d0380cd44014c9c715147705233b4db5a41200f26c53ee09d86`. A scan of that image, and of the three local tags above, found no named system certificate, no conf line, and no bundle whose text still names the root. OpenSSL does not read that subject from the system bundle. The entrypoints are unchanged.

A second read of the same change found paths that still started the old bytes:

- Serve was reading only an exported image variable. The pin in the gitignored env file, which is what compose interpolates, was not checked. Serve now reads that file too, and a one-shot bench uses the same check.
- The SYCL base `sha256:b763b3587a8fd40f7575d8a12b38071cc2ed8a88086925e6936da7727723412f` still has the root in Ubuntu's pip bundle. The new-host notes were telling a host to pin that digest and serve it. Those notes now say it is a build input. Serve refuses it, and doctor warns on it.
- The measured name `exl3xpu:b70-15ded2f` is not a digest, so the digest list cannot see a stale local build. Serve scans that name for the root before starting it.
- The rebuild now copies `uv` and `uvx` as two binaries. A directory that cannot be listed, or a file that cannot be read, fails the build. The scan includes `/home`, `/srv`, `/var`, `/app`, and `/workspace`. Wheel caches under those trees are removed.
- A `uvx` on `PATH` older than 0.13.4 is refused, the same way an old `uv` is. The harness asks `uvx --version` before it will load. A dry-run stand-in answers that probe and records a call only when the bench actually runs.

The certificate file in the system store does not contain the root's name as text. OpenSSL reads it from the certificate itself. The file is `/usr/share/ca-certificates/mozilla/emSign_ECC_Root_CA_-_G3.crt`, and `/etc/ca-certificates.conf` lists it. `update-ca-certificates` removes a certificate only when that line starts with `!`. Deleting the line and the file first leaves the symlink in place and reports that nothing was removed. The rebuild marks the line, rebuilds the store, then deletes the certificate, the symlink, any link whose target is that certificate, and the conf line, and rebuilds the store again. It does not copy the certifi bundle onto the system store, and it does not follow a symlink while replacing a bundle. A bundle that still contains the root's name as text, including one that is not named `cacert.pem`, is replaced. The build fails if the named certificate remains, if a link to it remains, or if OpenSSL still reads that subject from the system bundle. A text search misses a bundle that stores the root only inside the certificate. The rebuild asks OpenSSL for the subject of every `.pem`, `.crt`, and `.cer`, and it replaces a bundle whose subject is that root. `uv` and `uvx` are replaced and scanned in every top-level directory. The same subject check runs before the measured local image starts. A server that is already answering is kept only when its image id is the id that pin names. After the scan, serve starts that id, so a later retag of the name does not change the bytes.

### What this host still has

- `/bin/uv` and `/usr/bin/uv` are 0.12.24 and still contain the root. `/bin/uvx` and `/usr/bin/uvx` are the same version. A text scan of those two `uvx` files did not find the root's name. The harness still refuses them, because a `uvx` older than 0.13.4 is below the floor. None of them is the binary on `PATH` (`~/.local/bin/uv` and `~/.local/bin/uvx` are 0.13.5). The harness refuses to start if a shell puts an older binary first.
- Fedora's `python3` is 3.14.8, and the RPM pip is 26.0.1. That pip reads the system trust store, and the store on this machine does not contain the compromised root. Updating those RPMs needs administrator rights, which this session did not have. No `.python-version` file was added: pinning the managed 3.14.9 would change which interpreter `uv run` selects.
- Reinstalling Ubuntu's `python3-pip` inside a refreshed image would put the old bundle back. The serve path does not run apt. A rebuild of the Dockerfile is the way to restore the replacement.
